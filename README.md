___

1) Сбор данных:

   Источники котировок (alice, bob, chloe) представлены как web-socket контроллеры в IndigoTestTask.Host (SourceWebSocketController). При подключении клиентов контроллеры начинают отправлять тестовые сообщения.
   Есть возможность сконфигурировать RPS и частоту ошибок (разовый обрыв соединения, долговременный обрыв соединения, нарушение формата сообщения, дублирование).
   Формат сообщений уникален для каждого источника.

2) Обработка потока данных:

   Клиенты регистрируются как HostedService, объявлены в IndigoTestTask.Adapters (AliceDataSourceAdapter, BobDataSourceAdapter, ChloeDataSourceAdapter).
   Каждый клиент наследуются от базового класса адаптера, который в свою очередь приводит сообщения к доменной модели и пушит сообщение в кафку.

   Отказоустойчивость:
   1) Автоматическое переподключение обеспеченно через Polly (ResiliencePipeline)
   2) Реализован паттерн Outbox для решения проблем с ошибками брокера (kafka). Общий для всех клиентов (в production среде каждый клиент должен быть вынесен в отдельный микросервис с собственным Outbox)
  
   Чтение и парсинг сообщений из источников происходит в потоковом режиме.  

3) Хранение в БД
   Consumer тиков реализован в IndigoTestTask.App, класс DatabusTickBatchConsumerHandler.
   Потребляет данные из топика батчем и пишет в Postgre. Отсев дублей происходит на этапе записи в БД.
   Уникальность в рамках батча обеспечивается за счет приведения вставлеемой коллекции к hashSet-у.
   Уникальность в рамках БД проверкой хеш-суммы от всех полей котировки (индексируемое вычисляемое поле)

4) Базовый мониторинг
   TickProcessedChecker в проекте IndigoTestTask.App раз в 5 секунд выводит в лог количество записей в БД.
   Ошибки клиентов тоже пишутся в лог.

___

Реализация требований:
1) Обработка 50-100 тиков/сек (2-3 источника)
   - в текущей реализации спокойно переварит и 1000 RPS, далее потребуется увеличивать количество consumer-ов сообщений. Выше 10_000 RPS - уже начнем упираться в БД (стоит задуматься о шардировании, bulk)
2) Параллельная работа с несколькими WebSocket подключениями /Работа с WebSocket соединениями
   - в текущей реализации 3 источника и клиента. Все адаптеры наследуются от базового, не составит проблем добавить обработчик для нового источника данных.
3) Чистая архитектура, SOLID принципы / Расширяемость архитектуры для добавления новых бирж
   - реализована типовая луковая архитектура (паттерн адаптер). В production - можно было подумать о введении EventSourcing в связке с CQRS, если требуется историчность событий для каждого тикера.
4) Обработка обрывов соединения и автоматическое переподключение, отказоустойчивость
   - Polly (ResiliencePipeline)
5) Многопоточность и асинхронная обработка
   - внедрен брокер сообщений (kafka) - простор для асинхронной обработки и горизонтального мастштабирования практически не ограничен
6) Производительность и эффективность работы с БД
   - проверка на дубликаты производится по индексу от хеша сообщения (индекс не висит на всех полях), вставка новых сообщений производится батчами.
     для повышения отзычивости БД можно рассчитывать хеш на стороне кода, ввести кеш (InMemory/Redis), но в рамках тестового задания считаю избыточным
7) Покрытие тестами базовых сценариев
   - добавлены тесты на конвертеры и интеграционный тест на flow с записью дублей тиков в брокер. Как таковой бизнес-логики в решении нет, считаю данные кейсы необходимым и достаточными для проверки.
    В production среде определенно стоит покрыть unit-тестами адаптеры (в текущей реализации адаптеры ощутимо зависят от статических методов из-за чего проблематично покрыть их моками)
